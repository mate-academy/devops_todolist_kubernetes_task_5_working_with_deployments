# Django ToDo App - Kubernetes Deployment Instructions

Цей документ містить інструкції щодо розгортання додатку ToDo в кластері Kubernetes, а також пояснення вибраних архітектурних рішень.

## 1. How to deploy the app to k8s

Для розгортання додатку виконайте наступні кроки у вашому терміналі, де налаштовано доступ до кластера (через `kubectl`):

1. **Створіть namespace** (якщо він ще не створений):
   `kubectl create namespace mateapp`

2. **Застосуйте маніфест Deployment**:
   `kubectl apply -f deployment.yml`

3. **Застосуйте маніфест HPA (Horizontal Pod Autoscaler)**:
   `kubectl apply -f hpa.yml`

4. **Перевірте статус розгортання**:
   `kubectl get pods -n mateapp`
   `kubectl get hpa -n mateapp`

## 2. Explanation of Resource Requests and Limits

* **Requests (`memory: 64Mi`, `cpu: 100m`):** Це базові ресурси, гарантовані для запуску додатку. Python/Django у стані спокою (idle state) є відносно легким. 64 Мегабайти пам'яті та 0.1 ядра процесора цілком достатньо для старту контейнера без зайвого резервування ресурсів кластера.
* **Limits (`memory: 128Mi`, `cpu: 250m`):** Це жорстка межа, яка захищає кластер. Якщо в додатку станеться витік пам'яті або раптовий стрибок обчислень, він не зможе спожити більше ніж 128Mi RAM або 250m CPU, і не вплине на інші сервіси на тій самій ноді (node).

## 3. Explanation of HPA Configuration

* **Minimum pods (2):** Забезпечує високу доступність (High Availability). Якщо один Pod впаде або нода вийде з ладу, другий продовжить обробляти запити, що гарантує відсутність простоїв (zero-downtime).
* **Maximum pods (5):** Обмежує максимальне масштабування, щоб захистити кластер від надмірного використання ресурсів у випадку DDoS-атаки або нетипового сплеску трафіку.
* **Metrics (CPU & Memory at 70%):** Масштабування спрацьовує, коли середнє навантаження досягає 70%. Цей запас у 30% дає системі достатньо часу на запуск нових Pod'ів (враховуючи час на проходження `initialDelaySeconds` у liveness/readiness пробах), перш ніж поточні Pod'и перестануть відповідати.

## 4. Explanation of Strategy Configuration (RollingUpdate)

Для оновлення додатку обрано стратегію **RollingUpdate** з наступними параметрами:
* `maxUnavailable: 1`
* `maxSurge: 1`

**Чому такі числа?** 
Оскільки наш базовий стан — це 2 Pod'и, `maxUnavailable: 1` гарантує, що під час оновлення принаймні 1 Pod завжди залишатиметься активним для обслуговування користувачів. `maxSurge: 1` дозволяє Kubernetes створити лише 1 додатковий новий Pod понад бажану кількість (загалом 3 під час оновлення), що не перевантажує кластер запитами на ресурси. Ця стратегія забезпечує плавне оновлення без перебоїв у роботі сервісу.

## 5. How to access the app after deployment

Оскільки в завданні не було створено ресурс Service або Ingress, найпростіший спосіб отримати прямий доступ до розгорнутого додатку для тестування — використати `port-forward`.

Виконайте цю команду в терміналі:
`kubectl port-forward deployment/kube2py 8080:8080 -n mateapp`

Після цього ви зможете відкрити браузер і перейти за адресою:
[http://localhost:8080](http://localhost:8080) для перегляду UI або взаємодії з API.
