# INSTRUCTION.md

Інструкція з розгортання ToDo застосунку в Kubernetes у namespace `mateapp`.

> Значення ресурсів та порогів HPA нижче — приклад із розумними дефолтами для легкого веб-застосунку. Якщо у вас інші реальні числа в `deployment.yml`/`hpa.yml`, підставте свої — і відповідно скоригуйте пояснення.

## 1. Передумови

- Встановлений і налаштований `kubectl` з доступом до кластера.
- У кластері має бути розгорнутий **metrics-server** — без нього Horizontal Pod Autoscaler не зможе отримувати метрики CPU/Memory і не працюватиме.
- Namespace `mateapp` (буде створений на кроці 2, якщо ще не існує).

## 2. Кроки розгортання

1. Створіть namespace (якщо його ще немає):
   ```bash
   kubectl create namespace mateapp
   ```
2. Застосуйте Deployment:
   ```bash
   kubectl apply -f deployment.yml
   ```
3. Застосуйте Horizontal Pod Autoscaler:
   ```bash
   kubectl apply -f hpa.yml
   ```
4. Перевірте, що поди піднялись і HPA бачить метрики:
   ```bash
   kubectl get pods -n mateapp
   kubectl get hpa -n mateapp
   kubectl describe hpa <hpa-name> -n mateapp
   ```
   У ідлі маєте побачити **2 запущені поди**.

## 3. Обґрунтування Resource Requests та Limits

```yaml
resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    cpu: 250m
    memory: 256Mi
```

- **Requests (100m CPU / 128Mi RAM)** — це базове (гарантоване) споживання ресурсів для легкого ToDo-застосунку в стані очікування запитів. Саме ці значення scheduler використовує, щоб вирішити, на яку ноду помістити под, і саме на requests орієнтується HPA при розрахунку відсотка утилізації.
- **Limits (250m CPU / 256Mi RAM)** — приблизно у 2–2.5 рази більше за requests. Це дає застосунку запас на короткочасні сплески навантаження (наприклад, кілька одночасних запитів), не дозволяючи одному поду "з'їсти" всі ресурси ноди. CPU-limit спричиняє throttling при перевищенні, Memory-limit — OOMKill поду, тому важливо, щоб limit не був занадто близьким до requests (інакше под буде часто вбиватися) і не занадто великим (інакше зникає сенс обмеження).
- Таке співвідношення requests:limits дозволяє тримати **2 поди в ідлі** комфортно на невеликій ноді, залишаючи ресурс для масштабування вгору при рості навантаження.

## 4. Обґрунтування конфігурації HPA

```yaml
minReplicas: 2
maxReplicas: 5
metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 75
```

- **`minReplicas: 2`** — навіть без навантаження застосунок має мінімум 2 репліки. Це базова відмовостійкість: якщо один под впаде (краш, оновлення ноди тощо), другий продовжує обслуговувати трафік без даунтайму.
- **`maxReplicas: 5`** — обмежує масштабування зверху, щоб уникнути неконтрольованого споживання ресурсів кластера при аномальному навантаженні або баг-циклі. 5 подів достатньо для очікуваного піку трафіку невеликого ToDo-застосунку.
- **CPU + Memory одночасно** — використано `autoscaling/v2`, що дозволяє задати кілька метрик. CPU показує обчислювальне навантаження (кількість запитів, що обробляються), а Memory — накопичення стану, кешів чи потенційні витоки пам'яті. Разом вони дають надійніший сигнал для масштабування, ніж лише одна метрика: якщо спрацьовує будь-яка з двох, HPA додає поди.
- **Пороги 70% (CPU) / 75% (Memory)** — обрані так, щоб масштабування спрацьовувало заздалегідь, до того як под почне деградувати по продуктивності, але не занадто рано (щоб не було зайвого "тремтіння" — постійного скейлу туди-сюди при незначних коливаннях).

## 5. Обґрунтування стратегії RollingUpdate

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0
```

- **`maxUnavailable: 0`** — під час оновлення жоден із існуючих подів не вимикається, поки новий не стане готовим (Ready). Це гарантує **нульовий даунтайм**: користувачі весь час мають доступ до працюючого застосунку.
- **`maxSurge: 1`** — дозволяє тимчасово створити 1 додатковий под понад бажану кількість реплік, щоб новий под встиг запуститись і пройти readiness-перевірку, перш ніж старий буде видалено. Тобто під час оновлення 2 подів кількість тимчасово зросте до 3, а потім плавно повернеться до 2.
- Такі значення — компромісний варіант для невеликого застосунку: оновлення проходить безпечно (без втрати доступності) і без значного тимчасового overhead по ресурсах (лише +1 под, а не подвоєння).

## 6. Доступ до застосунку після деплою

Якщо застосунок відкритий через Service (`ClusterIP`), найпростіший спосіб перевірити роботу локально — port-forward:

```bash
kubectl port-forward svc/<service-name> 8080:80 -n mateapp
```

Після цього застосунок буде доступний у браузері за адресою:

```
http://localhost:8080
```

Якщо у кластері налаштований Ingress з доменним ім'ям, застосунок буде доступний напряму за цим доменом (наприклад `https://todo.example.com`) — у такому випадку port-forward не потрібен, достатньо переконатись, що DNS/Ingress-правило вказує на Service застосунку в namespace `mateapp`.

Щоб перевірити, який Service та порти доступні:
```bash
kubectl get svc -n mateapp
```
